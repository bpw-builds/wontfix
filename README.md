# wontfix

Your coding agent keeps proposing the thing you already tried three chats ago.

wontfix is a ledger of decisions and dead ends that lives in your repo. The agent writes to it as it works. Claude Code, Cursor and Codex each load it back at the start of every session, automatically.

```bash
npm install -g wontfix
wontfix init
```

`npx wontfix init` works too, but install it globally if you can. The session-start hook shells out to wontfix every time a session opens, and without a local copy npx refetches it on each one, which costs a second or two and fails outright with no network.

## What ends up in it

Real entries look like this:

```
wontfix     redis for the job queue
            reason: 400ms cold start on the free tier

wontfix     websockets for live updates
            reason: blocked by the corporate proxy at the pilot customer

wontfix     zod for request validation
            reason: added 40kb to the edge bundle, we were at the limit

constraint  never write to the billing table directly, use the ledger service

decision    poll every 5s instead of streaming
            reason: works behind proxies, cost is fine at this scale
```

Every one of those cost somebody an afternoon. None of them are in your README, and none of them survive a new chat window.

By default the ledger is committed to git, so a public repo publishes your dead ends along with your code. That is usually what you want on a team, and clearly not what you want sometimes. `wontfix init --private` keeps it out of git entirely.

## What the agent actually sees

```markdown
## Project context (generated by wontfix)

### Already tried and rejected. Do not propose these again.
- redis for the job queue. Reason: 400ms cold start on the free tier
- websockets for live updates. Reason: blocked by the corporate proxy at the pilot customer

### Rules that must hold.
- never write to the billing table directly, use the ledger service

### Decisions already made.
- poll every 5s instead of streaming. Reason: works behind proxies, cost is fine at this scale

<!-- wontfix: 12 of 19 entries packed. 7 omitted (5 state, 2 decision). Budget 1200. -->
```

That last line is the point. The ledger grows without limit, the context does not, and you can see exactly what got cut and why.

## Why not just a CLAUDE.md

You already have one, and the agent still misses half of it. Two differences here.

The agent writes the entries itself, as it hits them, so nobody has to stop mid-problem to document. And `pack` ranks what it has and cuts it to a token budget, so the context that gets loaded is short enough to actually be read.

Rejected approaches rank highest. Current state ranks lowest and expires, because stale state is worse than no state at all.

Plain-text project memory for agents is not a new idea. projectmem and Codified Context both explore it, and every serious repo already has some version of a conventions file. What is specific here: every rejection carries the reason that killed it, the context is ranked and cut to a budget rather than pasted whole, the agent writes entries as a side effect of working, and the whole thing travels through git like code.

## Is it working

The honest question after two weeks is whether the ledger fills itself or quietly dies. There is a command for that:

```bash
$ wontfix stats
Entries        34 total, 29 live
Written by     27 agent, 7 human
Agent share    79%
Last 7 days    9 entries (8 by agent)
Rate           11.9 per week, 9.4 by agent
Age            21 days since first entry
Web export     current as of Aug 14

Healthy. The agent is filling this on its own.
```

If the agent number is near zero after a week of real work, nothing else about the tool matters. Delete it or tell the agent to start recording.

## Commands

```bash
wontfix add wontfix "redis for the job queue" --why "400ms cold start"
wontfix add constraint "never write to the billing table directly"
wontfix add decision "postgres over mongo" --why "we need real transactions"
wontfix add state "auth migration half done, /login is new"

wontfix pack --budget 1200      # the context block
wontfix export --copy           # same block, sized for browser chats
wontfix list                    # human readable
wontfix stats                   # is the agent actually using this
wontfix why "redis"             # the reason, plus a link to the commit
wontfix backfill                # propose entries from git history
wontfix revoke <id>             # retire an entry
```

`--why` is required on `wontfix` and `decision`. An entry with no reason is a rule nobody can ever overturn.

Add `--durability permanent` for things that outlive the project, or `session` for notes that should expire in two weeks. Default sits in between.

## Starting from an existing repo

An empty ledger is the main reason people give up in week one. Your git history already holds the answer:

```bash
wontfix backfill
```

It reads reverts, rollbacks and migrations, and prints what it found. It writes nothing until you run `wontfix backfill --apply`, and it drops any candidate whose commit message never said why, because a prohibition nobody can evaluate is worse than a gap.

Backfilled entries are tagged `source: git` and excluded from the agent share in `stats`, so mining your history cannot flatter the one number that tells you whether the tool works.

## Closing the fourth duplicate pull request

```bash
$ wontfix why "redis"
wontfix: redis for the job queue
  reason: 400ms cold start on the free tier
  recorded: 2026-08-03 by agent
  source: https://github.com/acme/thing/blob/bbc7e83e/.wontfix/ledger.jsonl
```

Paste the link. The argument was already had, and now it has a permanent address.

## Hook details

`init` installs a session-start hook for all three agents:

| Tool | Config it writes | Event |
|---|---|---|
| Claude Code | `.claude/settings.json` | `SessionStart` |
| Codex | `.codex/hooks.json` | `SessionStart` |
| Cursor | `.cursor/hooks.json` | `sessionStart` |

Claude Code and Codex share a hook shape, so they run the same command. Cursor expects `additional_context` instead of `hookSpecificOutput`, so it gets `--format cursor`. Existing hooks in any of those files are preserved, and a config that is not valid JSON is refused rather than overwritten.

```bash
wontfix hook status                  # which tools are wired up
wontfix hook install --only cursor   # just one
wontfix hook remove                  # take them all back out
wontfix init --no-hook               # never install them
```

`init` also writes the rules into `AGENTS.md`, which Codex, Cursor, Aider, Jules, Zed and others read natively, so one file covers most tools. Some repos explicitly forbid adding guidance to `CLAUDE.md` or Cursor rules, so those are opt in:

```bash
wontfix init --guidance agents,claude,cursor
```

## Using it in browser chats

The ledger is written by the CLI in a repo. If you also talk to Claude, ChatGPT or Gemini in a browser about that same project, you can carry it over:

```bash
wontfix export --copy
```

That puts a block on your clipboard. Paste it into your project instructions, replacing any previous wontfix block. Every conversation in that project then starts with the same rejected list your agent sees in the terminal.

```markdown
## Project context (generated by wontfix)

Rule: do not propose anything in the rejected list below. If a reason looks out
of date, say so instead of quietly following it.

### Already tried and rejected. Do not propose these again.
- redis for the job queue. Reason: 400ms cold start on the free tier

<!-- wontfix export: 12 of 19 entries, budget 600, 2026-08-17. Re-run "wontfix export" if this looks stale. -->
```

The budget defaults to 600 rather than 1200, because instructions fields are much smaller than an agent context window and oversized pastes get truncated without telling you.

This is read-only and deliberately so. The browser cannot write back to your ledger, which means the pasted block is a cache, not a second source of truth. Caches go stale, so `stats` tells you when:

```
Web export     14 entries added since your export on Aug 3
```

Re-run `wontfix export --copy` and paste again. If you have no repo and no CLI, wontfix has nothing to offer you yet.

## Where it lives

`.wontfix/ledger.jsonl`. One JSON object per line, append only, so the whole team shares one memory. Nothing is deleted or rewritten, which keeps `git diff` readable and means two agents in two terminals cannot corrupt each other.

`.wontfix/export.local.json` records when you last exported. It is per person, so `init` adds it to `.gitignore`.

## Security

The ledger arrives through git, gets injected into an agent's context at session start, and is written by an agent rather than a person. That is a real trust surface, so here is what is handled and what is not.

**Handled.** Entry text is flattened on the way in: newlines, tabs, ANSI escapes, C0 and C1 control characters, zero width and bidi overrides all go, and leading markdown structure is stripped. Without that, one entry containing a newline followed by `### Rules that must hold.` forges a whole section in the pack that the agent reads as instructions. The same sanitizer runs again at render time, so a hand-edited or pulled line gets the same treatment. Credentials are scrubbed before anything reaches disk, anchored to recognizable prefixes so ordinary debugging prose survives. No user string ever reaches a shell: every subprocess is `spawnSync` with an argv array, and no code path uses `shell: true` or `exec`. Ids are validated against a fixed character set before they are handed to git. The ledger and the export marker are written owner only, in an owner only directory. Reads are capped at 16MB, and past that the tail is read and you are told, rather than the process aborting mid session start.

**Not handled, by design.** A pull request can add a plausible-looking entry, and once merged, every teammate's agent treats it as standing context. Sanitizing the text does not make the content trustworthy. Review changes to `.wontfix/ledger.jsonl` the way you would review a change to CI config or a git hook, and be especially careful with first-time contributors.

A pull request can also append a line reusing an existing entry id with `status: revoked`, which silently retires a real rejection. Nothing is deleted, so the forgery is in the diff and in history, and `stats` reports the revocation count so a jump is visible. But nothing blocks it. Same review rule applies.

Anything already pushed stays in git history. `init --private` adds a gitignore line and warns if the ledger is already tracked, but it cannot un-publish what you have committed.

## Limits worth knowing

Agents follow the rules most of the time, not always. When `stats` looks thin, tell the agent to record what it just learned.

A rejection ledger can turn into dogma. Reasons go stale, you leave the free tier, and the 400ms objection stops being true. The rules tell the agent to challenge an entry whose reason no longer holds, and `revoke` exists for when it doesn't.

Hook support differs by tool and moves fast. Cursor's `sessionStart` fires for local agent sessions but not for cloud agents. Codex hooks do not run on Windows. If `hook status` says installed and nothing appears in your session, check the tool's own hooks panel or log first.

Token counts are estimated at four characters per token. Close enough for a budget, not a real tokenizer.

No accounts, no server, no telemetry, no network calls. Everything stays in your repo.
